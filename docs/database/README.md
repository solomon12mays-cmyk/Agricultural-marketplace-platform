# Database Schema Structure

The platform stores all application data in PostgreSQL inside a single
dedicated schema: **`marketplace`**. Flyway owns the schema lifecycle; every
table change is expressed as a versioned migration in
`backend/src/main/resources/db/migration`.

See [schema.md](./schema.md) for the full table reference and ERD.

## Conventions

| Concern | Convention |
| --- | --- |
| Schema | `marketplace` (Flyway `default-schema`, Hibernate `default_schema`) |
| Primary keys | `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| Naming | `snake_case` tables and columns; plural table names |
| Timestamps | `created_at` (required) and `updated_at` where rows mutate |
| Money | `NUMERIC(19, 2)` + separate `currency VARCHAR(8)` |
| Quantities | `NUMERIC(19, 3)` for stock, `NUMERIC(10, 2)` for sizes |
| Enums | `VARCHAR` columns validated by the application state machines |
| Soft state | Status columns mirror the backend state machines, not DB triggers |
| Referential integrity | Foreign keys + indexes on every FK column |

## Evolution rules

1. Never edit an applied migration — add a new `Vnn__description.sql`.
2. Migrations must apply cleanly on both PostgreSQL 16 (production) and
   H2 in PostgreSQL mode (local/tests).
3. Hibernate runs with `ddl-auto: validate`: every entity column must exist
   after migration, and every new column must be added in the same change
   set as its entity.
4. Index every foreign key; use `UNIQUE` constraints for natural keys
   (username, national_id, plate_number, slug, idempotency_key).
5. Data migrations (backfills) live in their own numbered migration,
   separate from DDL.
